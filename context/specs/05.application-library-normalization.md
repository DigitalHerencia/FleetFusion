# Spec 05 — Maintain Application Library Boundaries

**Priority:** P5  
**Depends on:** Spec 04

## Issue intent

Keep the current `lib/`, `schemas/`, and `types/` responsibilities coherent as the application evolves.

This is maintenance of an implemented structure, not a mandate to create missing symmetry.

## Actions

Current action files include domain/responsibility families such as:

```text
adminActions.ts
aiActions.ts
commonActions.ts
crmActions.ts
invoicingActions.ts
marketingActions.ts
onboardingActions.ts
portalActions.ts
projectsActions.ts
socialActions.ts
supportActions.ts
```

Do not create `userActions.ts` or another file merely because an older target list included it.

## Fetchers

Current fetcher files include:

```text
adminFetchers.ts
aiFetchers.ts
crmFetchers.ts
integrationFetchers.ts
invoicingFetchers.ts
marketingFetchers.ts
onboardingFetchers.ts
organizationFetchers.ts
portalFetchers.ts
projectsFetchers.ts
socialFetchers.ts
supportFetchers.ts
```

Keep reads in the existing appropriate family.

## Workflows

`lib/workflows` owns application/domain orchestration that combines lower-level operations.

Do not collapse workflows into actions or duplicate them in features.

## Database library

Preserve the implemented database runtime:

```text
lib/db/
├── client.ts
├── provider.ts
├── tenant.ts
├── selects/
├── dto/
└── transactions/
```

Do not delete `provider.ts` or `tenant.ts` merely because an older conceptual diagram did not list them.

## Auth and authz

Preserve:

```text
lib/auth
lib/authz
```

Clerk-specific identity behavior stays under auth.

Application roles, permissions, resources, and policies stay under authz.

## Integrations

Provider adapters remain under:

```text
lib/integrations
```

with existing Clerk/Neon/Prisma exceptions.

## Schemas

Current runtime schemas are domain/cross-cutting files such as:

```text
adminSchemas.ts
aiSchemas.ts
commonSchemas.ts
crmSchemas.ts
integrationSchemas.ts
invoicingSchemas.ts
marketingSchemas.ts
portalSchemas.ts
projectsSchemas.ts
socialSchemas.ts
supportSchemas.ts
```

Preserve useful current organization.

## Types

Current shared types include domain and cross-cutting files such as:

```text
access.ts
adminTypes.ts
aiTypes.ts
commonTypes.ts
crmTypes.ts
integrationTypes.ts
invoicingTypes.ts
marketingTypes.ts
portalTypes.ts
projectsTypes.ts
socialTypes.ts
supportTypes.ts
uiTypes.ts
```

Do not force every schema family to have an identically named type family or vice versa.

## Acceptance criteria

- [ ] Existing action/fetcher/workflow responsibilities remain coherent.
- [ ] `lib/db/provider.ts` and `lib/db/tenant.ts` are recognized as implemented responsibilities.
- [ ] Auth/authz boundaries remain distinct.
- [ ] Provider adapters remain isolated.
- [ ] Schema/type organization reflects actual shared contracts.
- [ ] No symmetry-only files are introduced.
- [ ] No parallel repository/service architecture is introduced without owner approval.
- [ ] Webhook persistence continues to use the existing Route Handler/auth/transaction boundaries.
