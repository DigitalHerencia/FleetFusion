# Spec 00 — Maintain the Implemented Architectural Contract

**Priority:** P0

## Issue intent

Keep governance and future implementation work aligned with the architecture that currently exists in the Maximal Template.

This issue does not authorize refactoring the codebase to match an older governance model.

## Current baseline

The application currently uses:

```text
app/
components/
features/
lib/
schemas/
types/
prisma/
```

The presentation architecture includes:

```text
components/ui
components/blocks
components/templates
components/chart
components/brand
components/nav
components/shells
features
```

The server/application architecture includes:

```text
lib/fetchers
lib/actions
lib/workflows
lib/db
lib/auth
lib/authz
lib/integrations
schemas
types
```

## Required behavior

When implementing future work:

- preserve existing responsibility boundaries unless the owner explicitly changes them;
- do not remove `components/templates` from the architecture;
- do not force every route or feature through every presentation layer;
- allow blocks to own local presentation/demo interaction;
- keep application database, authorization, and provider authority outside generic presentation components;
- preserve thin route entrypoints where features already own orchestration;
- preserve existing domain-oriented fetcher/action/schema/type organization;
- use workflows for orchestration already expressed as workflows;
- preserve the current tenant authentication/onboarding gate.

## Architecture interpretation

Valid presentation paths include:

```text
app → feature → template → blocks/ui
app → template → blocks/ui
feature → template
feature → block
feature → ui
template → blocks/ui
block → ui
```

Responsibility matters more than mandatory traversal.

## Access model

Public informational/auth routes may be accessed without tenant admission.

Tenant surfaces require:

```text
authenticated application identity
+ completed onboarding
```

Resource-level authorization remains necessary after the tenant-layout gate.

## Acceptance criteria

- [ ] Governance describes the current route, presentation, server, auth, and provider boundaries.
- [ ] `components/templates` is represented as a first-class layer.
- [ ] No rule requires signed-out access to tenant surfaces.
- [ ] No rule requires blocks to be stateless or forbids local presentation/form interaction categorically.
- [ ] No rule invents route segments that do not exist.
- [ ] No rule creates symmetry-only files or layers.
- [ ] Implementation changes are not made solely to satisfy stale governance.
- [ ] Any intentional architectural change is owner-authorized before governance treats it as canonical.
