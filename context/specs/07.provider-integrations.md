# Spec 07 — Maintain External Provider Integrations

**Priority:** P7  
**Depends on:** Spec 06

## Issue intent

Maintain the provider integrations that currently exist without treating installed code as proof of live configuration.

## Current provider families

Provider adapters currently exist for:

```text
lib/integrations/cloudinary
lib/integrations/hugging-face
lib/integrations/sendgrid
lib/integrations/stripe
lib/integrations/vercel-blob
lib/integrations/status.ts
```

Specialized boundaries remain:

```text
Clerk  → lib/auth
Neon   → lib/db
Prisma → lib/db runtime + prisma lifecycle
```

## HTTP boundaries

Current API families include:

```text
app/api/ai
app/api/clerk
app/api/sendgrid
app/api/stripe
```

Route Handlers own HTTP request/response lifecycle and provider verification where applicable.

Reusable provider mechanics belong in provider adapters/auth helpers.

Reusable atomic persistence belongs in the database transaction boundary.

## Environment contract

The implementation currently documents provider keys including:

```text
STRIPE_SECRET_KEY
STRIPE_WEBHOOK_SECRET
BLOB_READ_WRITE_TOKEN
CLOUDINARY_CLOUD_NAME
CLOUDINARY_API_KEY
CLOUDINARY_API_SECRET
SENDGRID_API_KEY
SENDGRID_FROM_EMAIL
SENDGRID_WEBHOOK_VERIFICATION_KEY
HUGGINGFACE_ACCESS_TOKEN
HUGGINGFACE_TEXT_MODEL
```

Keep `.env.example` synchronized with code.

Never place real credentials in the example file.

## Missing configuration

Missing optional provider configuration must fail narrowly.

Provider/status UI should distinguish states such as:

- configured;
- unavailable/missing configuration;
- demo-only;
- not provisioned;

according to what the implementation can actually prove.

Do not silently simulate a live provider success.

## Provider truth

Installed dependencies, adapter files, or successful static compilation do not prove:

- account provisioning;
- webhook registration;
- live credentials;
- production health;
- successful external delivery.

Report only evidence that was actually obtained.

## Live operations

Do not perform without explicit owner authorization:

- provider account provisioning;
- webhook endpoint mutation;
- secret creation/rotation;
- live billing operations;
- destructive external mutations;
- production deployment.

## Acceptance criteria

- [ ] Existing provider families remain isolated in their current boundaries.
- [ ] HTTP lifecycle remains in Route Handlers.
- [ ] Provider authenticity is verified before trusted webhook processing where required.
- [ ] `.env.example` matches implementation names.
- [ ] Missing optional configuration fails narrowly.
- [ ] Status surfaces do not expose secrets.
- [ ] Static code existence is not reported as live-provider proof.
- [ ] No live provider mutation occurs without explicit owner instruction.
