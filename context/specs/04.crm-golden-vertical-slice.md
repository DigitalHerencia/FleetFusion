# Spec 04 — Preserve CRM as the Reference Vertical Slice

**Priority:** P4  
**Depends on:** Spec 03

## Issue intent

Use the implemented CRM architecture as a reference example for a complete tenant-domain slice.

Do not rewrite CRM to match older proposed filenames when the current files already express the working pattern.

## Access

CRM is a tenant surface.

CRM routes inherit the tenant-layout requirement for:

- authenticated application identity;
- completed onboarding.

Resource-level authorization and tenant scope remain required inside the server application boundary.

There is no signed-out CRM requirement.

## Route pattern

CRM uses thin route entrypoints.

The contacts list currently follows the pattern:

```text
app/(tenant)/crm/contacts/page.tsx
  → Suspense
  → CrmContactsFeature
  → CRM workflow/data
  → CrmContactsTemplate
```

Use the existing route tree as the source of truth for supported CRM resources.

## Feature pattern

`features/crm/` contains server features, client companions, and skeletons.

Current naming uses CRM-prefixed files such as:

```text
crmContactsFeature.tsx
crmContactsFeature.client.tsx
crmContactDetailFeature.tsx
crmContactDetailFeature.client.tsx
crmContactDetailSkeleton.tsx
```

Preserve this naming style when extending the existing family unless the owner requests a rename.

## Workflow pattern

CRM orchestration lives in:

```text
lib/workflows/crmWorkflows.ts
```

Workflows may combine CRM fetchers and actions and own higher-level domain calculations or transitions.

## Fetcher/action boundaries

CRM persisted reads use:

```text
lib/fetchers/crmFetchers.ts
```

CRM mutation entrypoints use:

```text
lib/actions/crmActions.ts
```

Do not duplicate those persistence responsibilities inside route pages or presentation components.

## Persistence contracts

CRM-specific persistence helpers and contracts are represented through:

```text
lib/db/selects/
lib/db/dto/
schemas/crmSchemas.ts
types/crmTypes.ts
```

Use the existing contracts before creating another parallel model.

## Presentation

CRM server features adapt data for CRM templates under:

```text
components/templates/
```

Client companions own client interaction when required.

Do not bypass the existing template layer merely because an older spec expected a data-table block directly from the feature.

## Evidence

Authorization, RLS, and cross-tenant claims require evidence from the relevant boundary.

UI rendering is not proof of tenant isolation.

## Acceptance criteria

- [ ] CRM routes remain tenant-gated.
- [ ] CRM route pages remain thin.
- [ ] Server features continue to use the existing workflow/fetcher/action architecture.
- [ ] CRM templates remain part of the presentation flow.
- [ ] Client companions are used only where browser behavior exists.
- [ ] CRM schemas/types/selects/DTOs are reused rather than duplicated.
- [ ] Resource-level authz remains enforced at server boundaries.
- [ ] No anonymous CRM requirement is introduced.
- [ ] No CRM file is renamed solely to match an obsolete naming proposal.
