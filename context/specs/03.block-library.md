# Spec 03 — Maintain the UI, Block, and Template Libraries

**Priority:** P3  
**Depends on:** Spec 02

## Issue intent

Maintain the presentation architecture that actually exists.

Do not use this issue to delete working blocks or templates in order to restore an older “pure blocks only” model.

## Current presentation families

```text
components/ui/
components/blocks/
components/templates/
components/chart/
components/brand/
components/nav/
components/shells/
```

## UI requirements

`components/ui` owns reusable controls and lower-level UI infrastructure.

Keep shared behavior such as focus, density, accessibility, variants, and semantic tokens centralized where appropriate.

## Block requirements

`components/blocks` owns reusable composed UI.

A block may:

- compose primitives;
- accept typed props/slots;
- own local UI state;
- provide local demo interaction;
- provide reusable form-shaped presentation.

A block must not become an application service boundary for:

- database persistence;
- server authorization policy;
- tenant resolution;
- external provider account truth;
- cross-domain business workflow.

### Auth block

`components/blocks/auth-forms.tsx` is intentional.

It may provide local/self-contained form behavior for reusable presentation variants.

The real Clerk/RHF auth flows remain in `features/auth`.

Do not delete or relocate this block merely because it contains form-shaped UI.

## Template requirements

`components/templates` is a first-class layer.

Templates own complete presentation compositions for public and tenant surfaces.

They may compose blocks and UI and receive prepared data/callbacks from features.

Do not push server data access or authorization into templates.

## Feature composition

Features may import:

- templates;
- blocks;
- UI primitives;

according to the implemented surface.

No meaningless wrapper is required simply to satisfy a diagram.

## Acceptance criteria

- [ ] Existing active blocks are preserved unless a product/design change requires modification.
- [ ] `components/templates` remains a documented and supported layer.
- [ ] Blocks may retain local presentation state.
- [ ] Real auth/provider/database/authz behavior remains outside generic blocks/templates.
- [ ] Features may compose the presentation layer that actually fits the surface.
- [ ] No file is moved solely to satisfy an obsolete block-purity rule.
- [ ] Shared design tokens and accessibility behavior remain consistent.
